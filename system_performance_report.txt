================================================================================
           تقرير فحص وتأخير أداء النظام (qaatSystem Performance Audit)
================================================================================
تاريخ الفحص: 2026-09-16
هدف الفحص: تحديد وتوثيق الأسباب الرئيسية لبطء الواجهات وتأخر التنقل (من 900ms إلى 1.4s)
ملاحظة: هذا التقرير تشخيصي فقط، ولم يتم إجراء أي تعديل برمجي على ملفات النظام.

--------------------------------------------------------------------------------
1. المشاكل الشاملة في النظام وأسباب البطء الرئيسي (900ms - 1.4s)
--------------------------------------------------------------------------------

[1.1] التحميل التلقائي وتجميد الشبكة عند فتح الواجهات (Blocking Auto-Preload)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  عند تحميل أي صفحة تحتوي على Lookup، يتم استدعاء الدوال `lookupEnsureLoaded('unit')` أو غيرها تلقائياً أثناء تحميل الصفحة. تذهب الطلبات إلى الخادم وتجلب كائنات كاملة عبر كود غير مؤجل، مما يسبب تزاحماً مع الموارد الأساسية للصفحة (CSS / JS / DOM) ويطيل زمن جاهزية الشاشة (DOM Ready Time).

- الملف المستهدف:
  c:\Laravel\qaatSystem\public\js\shared\lookup.js

- طريقة الإصلاح:
  تأجيل تحميل القوائم (Lazy Loading / On-Demand Loading) بحيث لا يتم طلب البيانات من السيرفر إلا عند تفاعل المستخدم الفعلي مع النافذة المنبثقة (Modal Show Event) أو كتابة أول حرف في البحث.

- ماذا يصلح بالضبط:
  يلغي طلبات الشبكة غير الضرورية أثناء التحميل المبدئي للصفحة، مما يخفض وقت فتح وتجهيز الصفحة بمقدار 200ms - 400ms.


[1.2] غياب التقسيم وجلب البيانات الكاملة من السيرفر (Lack of API Pagination)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  استدعاءات الـ API الخاصة بجلب العناصر (الأصناف، العملاء، الموردين، الحسابات) تستخدم `.get()` في المتحكمات (Controllers) بدون حد أقصى (Limit) أو تقسيم (Pagination). مع نمو قاعدة البيانات، يتم جلب آلاف السجلات وتحويلها إلى JSON ثم نقلها عبر الشبكة، مما يستهلك ذاكرة السيرفر وعرض النطاق الترددي للشبكة.

- الملفات المستهدفة:
  1. c:\Laravel\qaatSystem\public\js\shared\lookup.js
  2. c:\Laravel\qaatSystem\app\Http\Controllers\Inventory\ItemController.php (في دوال list و search)
  3. c:\Laravel\qaatSystem\app\Http\Controllers\SupplierController.php (في دوال list و search)

- طريقة الإصلاح:
  تعديل دوال الـ Controller لاستخدام `paginate(25)` أو `limit(50)` مع دعم مؤشرات التصفح (Cursor / Page Pagination) في الواجهة الأمامية `lookup.js`.

- ماذا يصلح بالضبط:
  تقليل حجم استجابة الـ JSON من عدة ميجابايت إلى بضعة كيلوبايتات فقط، وتسريع استجابة السيرفر من 600ms إلى أقل من 50ms.


[1.3] إعادة بناء الـ DOM المستمرة وربط الأحداث بالصفوف (DOM Over-rebuilding & Event Binding)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  في دالة `lookupRenderRows` في `lookup.js`، يتم تفريغ شجرة الـ DOM بالكامل وإنشاء عناصر جديدة ل كل صف بشكل منفرد، ثم ربط `EventListener` خاص بكل صف (Row Listener). هذا العمل يضغط على الـ Main Thread في المتصفح ويسبب تجمداً لحظياً (UI Jank/Lag) أثناء الكتابة أو التنقل.

- الملف المستهدف:
  c:\Laravel\qaatSystem\public\js\shared\lookup.js

- طريقة الإصلاح:
  1. الاعتماد على تقنية `Event Delegation` عبر ربط مستمع الأحداث بجدول النتائج الرئيسي مرة واحدة بدلاً من ربطه ب كل صف.
  2. استخدام `DocumentFragment` أو تقنيات Virtual Scrolling لعرض السجلات.

- ماذا يصلح بالضبط:
  القضاء على تجمد المتصفح أثناء العرض (Rendering lag)، وتسريع تلميحات الواجهة واستجابتها بنسبة 60%.


[1.4] غياب تقنية Debouncing في مدخلات البحث (Un-debounced Search Inputs)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  حقل البحث في `lookup-modal.blade.php` يرسل طلب Ajax أو ينفذ فلترة مع كل حرف يتم كتابته (`keyup` / `input` event) فوراً وبدون أي تأخير محدد (Debounce Delay). كتابة كلمة من 5 حروف ترسل 5 طلبات شبكة متتالية وتسبب سباق طلبات (Race Conditions).

- الملفات المستهدفة:
  1. c:\Laravel\qaatSystem\resources\views\shared\lookup-modal.blade.php
  2. c:\Laravel\qaatSystem\public\js\shared\lookup.js

- طريقة الإصلاح:
  إضافة دالة `debounce` لتأخير تنفيذ البحث بمقدار 300ms إلى 350ms بعد توقف المستخدم عن الكتابة.

- ماذا يصلح بالضبط:
  تخفيض عدد الطلبات المرسلة للسيرفر بنسبة 80% أثناء البحث وتجنب الارتباك وتزاحم الردود.


[1.5] المعمارية وتعدد ملفات الـ JS وإعادة التحميل الكامل (Full Page Reloads & Unbundled JS)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  تعتمد الشاشات الحالية على التحميل الكامل للصفحة (Full Http Request) عند التنقل بين الشاشات، كما يتم استدعاء عشرات ملفات الـ JS بشكل فردي في ملف `app.blade.php`. كل استدعاء يتطلب طلب HTTP جديد ومرحلة Parsing جديدة للـ V8 Engine في المتصفح.

- الملفات المستهدفة:
  1. c:\Laravel\qaatSystem\resources\views\layouts\app.blade.php
  2. ملفات الـ JS في مجلد `public/js/`

- طريقة الإصلاح:
  1. تجميع وتصغير ملفات النص البرمجي (Bundling & Minification) باستعمال Laravel Vite / Mix.
  2. تفعيل تقنيات التنسيق المؤجل (Defer Loading) أو تقنيات التنقل الجزئي (AJAX Page Loading / Turbolinks / SPA Wrappers).

- ماذا يصلح بالضبط:
  تقليل عدد طلبات الـ HTTP المبدئية عند التنقل وتخفيض زمن فتح الصفحة من 1.2s إلى أقل من 300ms.


--------------------------------------------------------------------------------
2. فحص ملفات دليل الحسابات وآلية عملها (Chart of Accounts Audit)
--------------------------------------------------------------------------------

[2.1] التكرار والاستعلامات المعقدة في شجرة الحسابات (Recursive Tree Operations)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  في ملف `CharAccountController.php` وتحديداً في دالتي `updateChildrenLevels` و `updateChildrenCodes` و `isDescendant`:
  يتم استدعاء استعلامات قواعد البيانات بشكل تكراري (N+1 Query Problem in Recursion) عند تعديل كود حساب أب أو نقل مستواه. إذا كانت الشجرة عميقة، يتم تنفيذ عشرات الاستعلامات المتتالية داخل الحلقة (Loop)، مما قد يسبب استهلاكاً عالياً للذاكرة وتأخراً كبيراً في الاستجابة.

- الملف المستهدف:
  c:\Laravel\qaatSystem\app\Http\Controllers\accounting\CharAccountController.php

- طريقة الإصلاح:
  1. استبدال الاستعلامات التكرارية بالاعتماد على استعلام تحديث جماعي باستعمال الـ Prefix/Like أو تقنيات Nested Sets / Materialized Path.
  2. الاستفادة من ميزة الـ Transactions و Batch Updates بدلاً من استدعاء `$child->update()` لكل عنصر على حدة داخل الحلقة التكرارية.

- ماذا يصلح بالضبط:
  تخفيض عدد الاستعلامات من N+1 استعلام إلى استعلام واحد أو استعلامين فقط عند تعديل أكواد الأبناء أو مستوياتهم.


[2.2] آلية توليد الأكواد الفرعية (generateChildCode Performance)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  دالة `generateChildCode` تقوم بجلب جميع أبناء الحساب الأب باستعمال `CharAccount::where('accParent', $parent->accountID)->get()` للحصول على أعلى كود وتوليد الكود التالي. جلب جميع الكائنات الكبيرة بالكامل من قاعدة البيانات لحساب مجرد رقم كود يعتبر استهلاكاً غير مبرر للذاكرة.

- الملف المستهدف:
  c:\Laravel\qaatSystem\app\Http\Controllers\accounting\CharAccountController.php

- طريقة الإصلاح:
  استخدام استعلام مباشر لجلب الكود الأقصى فقط:
  `CharAccount::where('accParent', $parent->accountID)->max('accCode')` أو `orderBy('accCode', 'desc')->value('accCode')`.

- ماذا يصلح بالضبط:
  توفير ذاكرة السيرفر وتقليل زمن توليد رقم الحساب الجديد بنسبة 90%.


[2.3] فلترة ومعالجة الشجرة في جانب العميل (Client-side Tree Rendering)
--------------------------------------------------------------------------------
- نوع الخلل وسببه:
  في `chartOfAccounts.js` يتم تحميل الشجرة التجميعية كاملة إلى الذاكرة عبر دالة `tree()` في `CharAccountController` ثم يتم فلترتها ورسمها في المتصفح باستخدام `renderTree()`. عند كثرة الحسابات الرئيسية والفرعية، تستغرق العمليات الحسابية والفلترة في الـ JS وقتاً ملموساً يضغط على المعالج.

- الملفات المستهدفة:
  1. c:\Laravel\qaatSystem\public\js\accounting\chartOfAccounts.js
  2. c:\Laravel\qaatSystem\app\Http\Controllers\accounting\CharAccountController.php

- طريقة الإصلاح:
  إضافة Caching (تخزين مؤقت) لنتائج الشجرة التجميعية في السيرفر (مثل Redis / Laravel Cache) مع إبطاله فقط عند إضافة أو تعديل أو حذف حساب.

- ماذا يصلح بالضبط:
  تسريع جلب شجرة الحسابات التجميعية واستجابتها للواجهة لتصبح فورية (أقل من 20ms).
