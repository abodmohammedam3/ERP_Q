## 🔴 ثانياً: Race Condition في رقم القيد

### الملف: `JournalEntryService.php` (السطر 56)

```php
// توليد رقم القيد
$nextEntryNo = (JournalEntry::max('entryNo') ?? 0) + 1;

DB::beginTransaction();  // ← بعد حساب الرقم!

try {
    $entry = JournalEntry::create([
        'entryNo' => $nextEntryNo,
        // ...
    ]);
```

### 🚨 المشاكل الثلاث:

**1. الحساب خارج الـ transaction:**
`max('entryNo')` يُنفَّذ **قبل** `beginTransaction`. أي طلب آخر يقرأ نفس القيمة.

**2. لا يوجد lock نهائياً:**
حتى مع `lockForUpdate` (الذي لم يُستخدم هنا)، المشكلة باقية كما رأينا مع Sales.

**3. لا يستخدم `SequenceService`:**
هذه **نفس المشكلة** التي أصلحناها في Sales/Purchase — لكنها موجودة هنا أيضاً!

### السيناريو المدمر:

| الزمن | Tab 1 | Tab 2 |
|-------|-------|-------|
| t=0 | يقرأ max=100 | — |
| t=1 | — | يقرأ max=100 |
| t=2 | ينشئ entryNo=101 | — |
| t=3 | — | ينشئ entryNo=101 |
| t=4 | **نفس الرقم!** | **نفس الرقم!** |

**النتيجة:** ميزان مراجعة بأرقام قيود مكررة = **كابوس محاسبي**.

### ✅ الإصلاح

```php
// 1. الحقن عبر Constructor
public function __construct(
    private SequenceService $sequences,
) {}

// 2. داخل create()
public function create(array $options): int
{
    // ... التحقق من التوازن
    
    return DB::transaction(function () use ($options) {
        // ← استخدم SequenceService
        $entryNo = $this->sequences->next('journal_entry');
        
        $entry = JournalEntry::create([
            'entryNo' => $entryNo,
            // ...
        ]);
        
        // ... إنشاء الأسطر (Bulk Insert)
        
        return $entry->entryID;
    });
}
```

## 🔴 ثالثاً: `localAmount` يُصبح صفراً عند التعديل

### الملف: `PaymentVoucherService.php` (السطر 128) و `ReceiptVoucherService.php` (نفس السطر)

```php
public static function update(int $id, array $data): ?PaymentVoucher
{
    // ...
    DB::beginTransaction();
    try {
        unset($data['voucherNumber']);
        
        JournalEntryService::deleteByDocNumber('PV-' . $voucher->paymentID);
        
        // 🚨 الكارثة:
        $data['localAmount'] = ($data['amount'] ?? 0) * ($data['exchangeRate'] ?? 1);
        
        $voucher->update($data);
```

### 🚨 السيناريو

**المستخدم يريد تعديل "الوصف فقط":**
```javascript
// Frontend يرسل
{
    "description": "دفعة جديدة"  // ← فقط هذا
    // لا amount ولا exchangeRate
}
```

**في الـ Backend:**
```php
$data['amount'] ?? 0           // = 0
$data['exchangeRate'] ?? 1     // = 1
$data['localAmount'] = 0 * 1;  // = 0 ← 🚨

$voucher->update($data);  // localAmount يصبح 0!
```

**النتيجة:**
- 🔴 `localAmount = 0` في قاعدة البيانات
- 🔴 ميزان المراجعة يُفسَد
- 🔴 التقارير تُظهر المبلغ صفر
- 🔴 القيد المحاسبي لا يتوازن (لأنه أعاد حسابه بناءً على 0)

### ✅ الإصلاح

```php
public function update(int $id, array $data): PaymentVoucher
{
    return DB::transaction(function () use ($id, $data) {
        $voucher = PaymentVoucher::findOrFail($id);
        
        unset($data['voucherNumber']);
        
        // ✅ احسب localAmount فقط لو تغيّر amount أو exchangeRate
        if (isset($data['amount']) || isset($data['exchangeRate'])) {
            $amount = $data['amount'] ?? $voucher->amount;
            $rate   = $data['exchangeRate'] ?? $voucher->exchangeRate;
            $data['localAmount'] = $amount * $rate;
        }
        
        // ✅ حذف القيد القديم
        $this->journalService->deleteByDocNumber('PV-' . $voucher->paymentID);
        
        $voucher->update($data);
        
        // ✅ إعادة إنشاء القيد
        $this->createJournalEntry($voucher);
        
        return $voucher->fresh();
    });
}
```

## 🔴 رابعاً: `Cache::lock` العام — يقتل الأداء

### الملف: `PaymentVoucherService.php` (السطر 26)

```php
$lock = Cache::lock('payment_voucher_create', 10);  // ← اسم ثابت!

if (!$lock->get()) {
    Log::warning('PaymentVoucherService@create: طلب مزدوج (Cache Lock)');
    return null;
}
```

### 🚨 المشكلة

الاسم `'payment_voucher_create'` **ثابت** — ليس مفتاحاً مشتقاً. النتيجة:

- 🔴 **مستخدم A** ينشئ سند صرف → يحصل على Lock
- 🔴 **مستخدم B** (عميل مختلف تماماً!) يحاول ينشئ سند → **يُرفض**
- 🔴 **مستخدم C** أيضاً يُرفض
- 🚨 النظام كله **serialized** على عملية واحدة في وقت واحد

### سيناريو واقعي:

**السبت صباحاً، 3 محاسبين يعملون:**
```
المحاسب 1: إنشاء سند → ✅ ينجح (يستغرق 50ms)
المحاسب 2: إنشاء سند → ❌ "طلب مزدوج" (بعد 20ms)
المحاسب 3: إنشاء سند → ❌ "طلب مزدوج" (بعد 10ms)
```

**مع 500 سند/ساعة متوقعة:**
- مع النظام الحالي: **500 طلب × 50ms = 25 ثانية serial**
- لكن المحاسبين سيرون أخطاء "طلب مزدوج" بدون سبب

### 🚨 المشكلة الأعمق

حتى `10 ثواني TTL` مشكلة:
- لو الاستعلام استغرق 11 ثانية (تحت ضغط)
- الـ Lock **يُحرَّر تلقائياً**
- عملية أخرى تكتسبه
- **Race Condition رجع!**

### ✅ الإصلاح الصحيح

**الـ Lock ليس الأداة.** الأداة الصحيحة = `SequenceService`:

```php
public function create(array $data): PaymentVoucher
{
    return DB::transaction(function () use ($data) {
        // ✅ 1. توليد الرقم ذرياً
        $data['voucherNumber'] = $data['voucherNumber']
            ?? $this->sequences->nextWithPrefix('payment_voucher', 'PV-' . now()->format('Ymd') . '-', 4);
        
        $data['voucherDate'] = $data['voucherDate'] ?? now()->toDateString();
        $data['localAmount'] = ($data['amount'] ?? 0) * ($data['exchangeRate'] ?? 1);
        
        // ✅ 2. لا حاجة لفحص "هل موجود" — SequenceService يضمن ذلك
        $voucher = PaymentVoucher::create($data);
        
        // ✅ 3. إنشاء القيد
        $this->createJournalEntry($voucher);
        
        return $voucher;
    });
}
```

**الفرق:**
- بدون Lock عام ✅
- بدون `LIKE 'PV-%'` ✅
- بدون فحص مكرر ✅
- يعمل بمعدل **thousands/sec** ✅

### الملف: `JournalEntryService.php` (السطر 100-120)

```php
public static function deleteByDocNumber(string $docNumber): bool
{
    try {
        $entries = JournalEntry::where('docNumber', $docNumber)->get();

    }

```

### 🚨 السيناريو المدمّر

**`PaymentVoucherService::update` يستدعيه داخل transaction:**

```php
DB::beginTransaction();
try {
    JournalEntryService::deleteByDocNumber('PV-1');  // ← يفشل داخلياً
    // لكنه يُرجع false، لا يرمي exception
    // فالكود يكمل بشكل طبيعي
    
    $voucher->update($data);
    self::createJournalEntry($voucher);  // ← يُنشئ قيد مكرر!
    
    DB::commit();  // ✅ ينجح!
} catch (...) { ... }
```

**النتيجة:**
- 🔴 القيد القديم **لم يُحذف** (لكن العملية نجحت)
- 🔴 قيد جديد **أُضيف**
- 🔴 **قيدان بنفس `docNumber`** = ميزان مراجعة مضاعف

### ✅ الإصلاح

```php
public function deleteByDocNumber(string $docNumber): void
{
    // ✅ بدون try/catch — الاستثناء ينتشر
    // ✅ داخل transaction المُستدعي
    $entryIds = JournalEntry::where('docNumber', $docNumber)
        ->pluck('entryID');
    
    if ($entryIds->isEmpty()) {
        return;
    }
    
    // ✅ Bulk delete — Query واحد
    JournalEntryLine::whereIn('entryID', $entryIds)->delete();
    JournalEntry::whereIn('entryID', $entryIds)->delete();
}
```

**المكاسب:**
- 2 queries بدل N×2 ✅
- الاستثناء ينتشر → rollback يعمل ✅
- ينضم لـ transaction المُستدعي تلقائياً ✅

## 🔴 سادساً: مشاكل إضافية في `JournalEntryController`

### 1. `session()->save()` على كل طلب

```php
public function index() { session()->save(); return view(...); }
public function list()  { session()->save(); ... }
public function show()  { session()->save(); ... }
```

**المشكلة:** هذا Workaround لـ `ReleaseSessionLock` middleware. يُشير إلى مشكلة أعمق في إدارة الـ Session.

**الحل:** حل مشكلة الـ Middleware، لا استدعاء `save()` في كل مكان.

### 2. Pagination مُعاد اختراعها

```php
$total = (clone $query)->count();
$lastPage = max(1, (int) ceil($total / self::PER_PAGE));
$page = min($page, $lastPage);
```

**مشاكل:**
- 2 Queries (count + fetch) بدل 1
- `clone $query` قد يُشغّل eager loads
- Laravel يوفر `paginate()` لهذا الغرض

**الحل:**
```php
$paginator = $query->orderByDesc('entryDate')
    ->orderByDesc('entryID')
    ->paginate(self::PER_PAGE);
```

### 3. N+1 في حساب `debit`/`credit` per entry

```php
foreach ($entries as $entry) {
    $debit  = (float) $entry->lines->sum('localDebit');  // ← في الذاكرة، OK
    $credit = (float) $entry->lines->sum('localCredit');
```

**بعد `with('lines')`:** لا N+1 — ✅ جيد.

**لكن:** لو الفاتورة فيها **500 سطر** × 10 entries = **5000 سطر** في الذاكرة لكل طلب.

**الحل:**
```php
$query->withSum('lines as total_debit', 'localDebit');
$query->withSum('lines as total_credit', 'localCredit');
```
Query واحد، بدون تحميل الأسطر كلها.

### 4. `search` — نفس مشكلة `LIKE '%x%'`

```php
->where('entryNo', 'like', "%{$search}%")
->orWhere('description2', 'like', "%{$search}%")
```

**الحل:** FULLTEXT على `description2` + index على `entryNo`, `docNumber`.

## 🟠 سابعاً: مشاكل عالية الأولوية

### 7.1: `generateVoucherNumber` — Full Table Scan

**الملف:** `PaymentVoucherService.php` (السطر 240)

### 7.2: `do-while` Loop في الترقيم

```php
do {
    $voucherNumber = 'PV-' . $today . '-' . str_pad($nextNumber, 4, '0', STR_PAD_LEFT);
    $exists = PaymentVoucher::where('voucherNumber', $voucherNumber)->exists();
```

**المشاكل:**
- Query إضافي لكل دورة
- لا يوجد upper bound → loop لا نهائي في حال خطأ
- ليس atomic → Race Condition

### 7.9: Balance check بحد `0.01` صارم

```php

```

**المشكلة:** مع `decimal:6`، الفرق المقبول يجب أن يكون أصغر بكثير. 

**مثال:**
- 1,000,000 USD × 0.0001 = 100 USD فرق
- القيد يُرفض لأن 100 > 0.01

**أو العكس:** فرق 0.005 يُقبل لكن يُسجّل مرتين = خطأ تراكمي.

**الحل:**
```php

```
